## Current Architecture Audit

### Mode manager, as present in this checkout

- `OperatingMode` contains `STOPPED`, `MANUAL`, `MAPPING`, `LOCALIZATION`, `NAVIGATION`, `STARTING`, `STOPPING`, `ERROR` (lowercase serialized values).
- `/mode/manual`, `/mode/mapping`, `/mode/localization`, `/mode/navigation`, `/mode/stop` are `std_srvs/Trigger`; `/mode/status` is transient-local/reliable `std_msgs/String` carrying plain enum values.
- `activate_mode()` serializes work under an `RLock`, requires `/simulation/status == running`, requires selected map for localization/navigation, rejects same-mode repeat with `Trigger.success=false`, stops current mode before target startup, enters STARTING, launches mode `ros2 launch` subprocess in new session, registers process ownership, sleeps a configured `startup_grace_period` (default 3 seconds), checks early process exit and owned descendants, then publishes target mode. Manual is a state-only path after stopping the prior process.
- Stop uses verified process group ownership and bounded SIGINT/SIGTERM/SIGKILL timeouts; failure publishes ERROR and preserves evidence. Simulation status leaving running stops current mode. A 0.5-second monitor detects unexpected launch-process exit, cleans/verifies descendants, and reports error (continue inspection of remaining method for final state semantics when implementation begins).
- Failure gaps to address in v0.1.4: only simulation and map presence are admission checks; no readiness/lifecycle/sensor/TF/nav-server/costmap/safety dependency contracts are consumed here; prior mode is stopped before target starts, so rollback/restart semantics are absent; sync sleep blocks the callback; public result is an unstructured Trigger boolean/string; repeated request is an error; goal activity is not visible in this manager; `/mode/status` conflates mode with transitional/error states; failed target can leave ERROR rather than a well-defined prior/stopped state. Process safety ownership itself should remain delegated to v0.1.1 lifecycle helpers.
- Launch targets: mapping `slam_mapping.launch.py`; localization `amcl_localization.launch.py`; navigation `nav2_navigation.launch.py`. Nav2 navigation launch itself includes Nav2 localization components (map server/AMCL) in this checkout, so dependency composition must account for shared stack/ownership and avoid duplicate localization launches.

## v0.1.4 Architecture

Use three separate state dimensions:

1. **Lifecycle** (v0.1.2): whether each manager/component is operational and has valid lifecycle history.
2. **Readiness** (v0.1.3): whether named dependencies currently meet contract, including reason/evidence.
3. **Operating mode** (v0.1.4): the commanded robot behavior state and transition transaction.

Do not add lifecycle or readiness states to the mode enum. The public runtime mode names remain `STOPPED`, `MANUAL`, `MAPPING`, `LOCALIZATION`, `NAVIGATION`; transitional states (STARTING/STOPPING) are transition phase, and degraded/error is health/status overlay per v0.1.3 readiness/lifecycle as supported. Tracker says DEGRADED/ERROR on dependency loss; exact representation needs compatibility review with v0.1.2/v0.1.3 contracts.

Proposed transition matrix. “Lifecycle operational” and each readiness dependency are named semantic requirements only; **concrete API is WAITING FOR V0.1.3 CONTRACT**. Navigation includes localization prerequisites because REQ-034 requires healthy localization and the navigation launch includes localization in this checkout. Manual preserves the command mux's existing priority policy. Stop should be fail-safe and generally allowed from any stable active state.

## v0.1.5 Architecture

Create a reusable pure health evaluation core (message observations + configured expectations → health result), then ROS adapters for LaserScan, Imu, Odometry, and TF. Publish structured health through the v0.1.3 readiness dependency mechanism only after contract reconciliation. Do not create a second readiness service/topic family.

Health dimensions warranted by tracker: missing/no samples, stale (age against ROS/simulation clock), invalid timestamp (zero, future beyond defined tolerance, non-monotonic), invalid frame, degraded rate (measured rolling window against expected rate), invalid scan ranges/covariance, odometry discontinuity/jump. `DUPLICATE_SOURCE` applies to source/TF authority observations where they can be distinguished; never claim per-edge source identity from TF payload alone. Derive stale bound from declared expected rate and tolerated missed samples (configurable, reviewed, and tested), not arbitrary startup sleep. For expected 10 Hz scan, a candidate bound is `N missed periods / 10 Hz`, but choose N from observed jitter baseline, clock behavior, and tracker acceptance before implementation. Use simulation ROS time for sim messages and detect paused `/clock` separately from sensor outage; monotonic wall time may bound watchdog execution but must not be compared directly to sim header stamps.

Sensor inventory above is authoritative for current files. Current repo does contain an IMU in xacro (50 Hz, `/imu/data`, `imu_link`) as well as LiDAR and controller odometry. Sensor health measures actual `header.stamp`, frame, rate, content, and covariance; configured update rates are expected baselines, not observed results. Sensor health never authorizes process signaling. Only verified lifecycle ownership permits stopping a process.

### TF ownership registry

### v0.1.6 EKF plan based on actual availability

Inputs supported by current configuration: `/diff_drive_controller/odom` (`nav_msgs/Odometry`) and `/imu/data` (`sensor_msgs/Imu`). No joint-derived odometry should be fused in addition to controller odometry; it is the same wheel measurement source. No ground truth input is permitted. Output should be a distinct topic such as `/odometry/filtered` (`nav_msgs/Odometry`) after confirming no established name contract; update consumers only deliberately. Use `world_frame=odom`, `odom_frame=odom`, `base_link_frame=base_link`, `map_frame=map`, `two_d_mode=true`, and `use_sim_time=true` in simulation. Candidate output frequency 30 Hz matches existing config, but measure and reconcile with input rates.

Measurement selection: wheel odometry provides planar forward velocity and yaw rate according to current `odom0_config`; consider covariance from controller and measured behavior before enabling additional pose terms. IMU should contribute yaw rate Z if frame/orientation/covariance semantics validate; use measured covariance and avoid double-counting derived yaw/velocity. Do not enable accelerations until bias/noise and covariance are validated. Differential/relative settings must be deliberately chosen: absolute wheel odom pose can accumulate drift; relative/differential policy needs benchmark evidence, not copied flags. Rejection thresholds should be justified using observed innovation/residual distributions and fault-injection behavior. Current YAML selects only wheel vx/vyaw and IMU vyaw, with `publish_tf:false`; this provides no fused TF today. v0.1.6 REQ-050 requires EKF to own odom→base_link: enable EKF TF and disable `diff_drive_controller.enable_odom_tf`; perform as one coordinated configuration switch, backed by duplicate and continuity gates.

Keep three streams distinct: **raw odometry** `/diff_drive_controller/odom`; **filtered** `/odometry/filtered`; **ground truth** evaluation-only simulator truth (source not yet confirmed). Record exact topics, bag metadata, clock mode, robot path, software/config hashes, and run identifiers. If no simulator truth topic is available, add/evaluate a bridge in v0.1.6 scope only after proving feasibility; never substitute filtered/raw odom for truth.

## Dependency Graph

```text
v0.1.1 verified process ownership
   └─ authorizes lifecycle-owned process cleanup only
v0.1.2 component lifecycle operational state/events
   └─ manager can act only when its owning lifecycle state permits
v0.1.3 readiness contracts and dependency evidence
   ├─ simulation readiness + LiDAR + odom → mapping admission
   ├─ valid map + sensors + TF + AMCL → localization readiness
   ├─ localization + costmaps + servers + safety path → navigation readiness
   └─ v0.1.5 sensor/TF observations become readiness dependencies
v0.1.4 mode state machine consumes lifecycle + readiness, owns commanded mode
v0.1.5 sensor/TF health provides evidence to readiness (and reports independently)
v0.1.6 EKF consumes raw odom + IMU, produces filtered odom/TF
   └─ v0.1.5 monitors raw and filtered streams; readiness may depend on filtered state
```

Avoid circularity: sensor health must not require localization/nav readiness; TF sensor health must not require the EKF output it is meant to assess. EKF health can be a separate readiness dependency. Navigation readiness can depend on localization readiness and filtered odometry, but EKF readiness must depend only on its raw inputs and own output diagnostics. Mapping uses raw wheel odometry until a later deliberate contract changes it. During navigation the AMCL/Nav2 stack may internally provide `map→odom`; mode admission must model that stack as one compatible dependency, not start a second localization owner.
